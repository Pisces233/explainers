1 · 分层

分层与运行时路径

请求从三个客户端进入同一个 SDK，经认证的 HTTP/SSE 到达唯一的 Host。Host 持有权限和事务，Engine 选择内置执行器或外部 Agent 适配器。内置执行器的原生记录最终落在 Workspace 的 runtime.sqlite，外部执行器保留自己的会话存储。

客户端应用 共享 UI / SDK Host 执行层 领域契约与能力库
清晰

单一权威

打开更多客户端不会多出调度器。关闭客户端时 Host 继续运行，执行、权限和清理只在 Host 和原生运行时里发生。

清晰

一套界面

Desktop 和 Mobile 共用 workbench-ui。尺寸只决定面板落位和密度，不切换页面结构。

边界

外部执行器保留原生运行时

Codex、Claude Code、外部 Pi 的会话历史留在它们自己的存储里，Ramulus 只保存来源限定的绑定和关联。

3 · 实体

主要实体关系

上半部分是 Host 级的组织数据，下半部分是每个 Workspace 自己的执行数据。两边不是同一个数据库，跨库关系（虚线）靠带作用域的引用维持，没有外键。

实线：外键或记录字段虚线：跨库引用绿色字段：标识原生记录的作用域是 {workspace_id, storage_id}

关系怎么读

关系基数代码约束
Project — Workspace1 : Nworkspace_owners 以 workspace_id 为主键，所以一个 Workspace 只有一个所有者
Project — MemberN : Mproject_memberships 可带 Profile，Member 分 human 和 agent

Agent — Conversation同一身份没有 Agent 表。{source: "ramulus", scope, conversation_id} 就是 Agent 引用

6 · 运行时

执行模型

沿代码追踪一条用户消息。内置和外部执行器在 Submission 之后分流，但都写同一套 Task 和 Entry。

  1. client · durable.ts

    SDK 校验后调用 POST …/conversations/:id/input，同时在 journal 留下原始命令。

  2. host · durable-workspace-routes.ts

    路由解析 durableConversationCommandSchema，取得 actor，核对地址和引用，并绑定请求生命周期。

  3. pi-runtime · submissions.ts

    submissions.submit 写入 Submission，状态从 queued 开始。

  4. pi-harness · inbox / generationexternal-agents · durable/input

    内置路径进入 pi.inbox Doc，由 pi.generation 调模型。绑定外部会话时走 ramulus.agent.external-input。

  5. pi-harness · tool.ts

    模型的每个工具调用创建一个 pi.tool 子 Task，一轮结束后 finishToolRound 决定下一次生成。

  6. pi-runtime · Entryclient · 活动流

    产出写成带 byTaskId 的 Entry，Submission 结算。客户端通过 …/activity/watch 看到变化。

10 · 分析

风险与建议

包级依赖和平台边界最稳。压力主要在 Host 内部：目录之间没有层次，组合逻辑集中在少数大文件里。

风险

Host 内部缺少层次

34 个目录互相可达，check:boundaries 管不到这里。建议先加目录级依赖检查，再从 models ↔ external-agents（27 / 25）和 conversations ↔ external-agents（15 / 19）拆起。

关注

组合文件过大

workspace-runtime.ts 4,329 行，service-control-state.ts 4,093 行，service.ts 3,162 行，durable-workspace.ts 2,791 行。可以沿现有领域目录下放，不新增转发层。

关注

外部 Agent 约 10 万行

external-agents 包 5.3 万行，Host 同名目录 4.9 万行，加起来接近全部源码的 9%。6 个文件超过 2,000 行，ramulus.agent.* 有 32 种记录类型。

关注

Companion 的归属偏向 Host

Companion 依赖 conversations 65 处、storage 47 处、organization 44 处。可以把规则继续收进 packages/companion，并通过窄端口访问 Host。

关注

测试分布不均

整体 1.26，Host 1.64，Desktop 1.81。workbench-ui 0.62、pi-runtime 0.55、wiki 0.33、web-access 0.19。调度器和共享 UI 值得先补。

关注

部分包仍是平铺结构

Core 约 3.3 万行、Client 约 4.1 万行直接放在 src/ 根目录，renderer/shared 有 5.7 万行。文件数继续增长后会更难定位。

清理

残留目录

packages/ramulus-pi-durable 没有 package.json，只剩 dist 和 node_modules，可以确认后删除。

信息

变更速度很快

11 月前 7 天有 439 次提交，比 10 月全月多 84%。大文件和目录环在这个速度下更容易产生冲突。

良好

包依赖无环

79 条包依赖全部指向内层，渲染层对 Host 的引用为 0，平台能力各归一层。
